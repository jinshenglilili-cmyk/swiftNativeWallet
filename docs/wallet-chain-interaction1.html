钱包处理 DApp 请求 - 与区块链交互流程

当钱包（原生应用）收到来自 DApp 的请求后，需要根据请求类型进行不同处理，最终与区块链节点交互得到结果，再返回给 DApp。本文档详细讲解整个处理流程。

一、整体处理流程

1️⃣ DApp → 钱包
DApp 通过 window.ethereum.request() 发起请求 → trust-min → window.trustwallet.postMessage → 原生钱包收到请求
↓
2️⃣ 钱包分类处理
根据请求方法判断类型：只读请求 / 授权请求 / 签名请求 / 交易请求
↓
3️⃣ 需要用户授权吗？
否 → 直接处理
是 → 弹出确认弹窗，等待用户操作
↓
4️⃣ 与区块链交互
只读请求 → 转发给 RPC 节点 → 直接返回结果
签名/交易 → 使用本地私钥签名 → 广播到节点
↓
5️⃣ 钱包 → DApp
结果通过 window.ethereum.sendResponse(id, result) 返回给 trust-min → trust-min resolve Promise → DApp 得到结果
核心设计思想：
  • 分层处理：trust-min 负责协议转换，原生钱包负责安全存储私钥和实际交互
  • 安全第一：私钥永远不离开原生环境，所有签名都在原生完成
  • 用户掌控：所有涉及签名和交易的操作必须经用户确认

二、请求类型分类

钱包收到的请求可以分为四大类，处理方式完全不同：

分类 方法举例 需要用户确认 需要私钥操作 与链交互
只读请求 eth_getBalance, eth_call, eth_blockNumber ❌ 不需要 ❌ 不需要 ✅ 需要（转发 RPC）
授权请求 eth_requestAccounts ✅ 需要 ❌ 不需要 ❌ 不需要
签名请求 personal_sign, eth_signTypedData_v4 ✅ 需要 ✅ 需要 ❌ 不需要（只签名不广播）
交易请求 eth_sendTransaction, eth_signTransaction ✅ 需要 ✅ 需要 ✅ 需要（签名后广播）

三、只读请求处理

只读请求 不改变链上状态，不需要用户授权，也不需要私钥，直接转发给区块链节点就可以了。

处理流程：直接转发 RPC

1. 原生收到请求：eth_getBalance，参数：[address, "latest"]
↓
2. 构建标准 JSON-RPC 请求： 
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "eth_getBalance",
  "params": ["0x...", "latest"]
}
↓
3. HTTP POST 发送到区块链节点 RPC 接口
↓
4. 节点返回 JSON-RPC 响应
↓
5. 取出 result 返回给 DApp
💡 为什么可以直接转发？
只读请求不需要访问私钥，也不需要用户确认，节点就能回答，所以不用钱包做额外处理，直接透传。

Swift 实现示例

func forwardToRPC(method: String,
             params: Any,
             id: Int,
             rpcURL: URL)
async throws -> Any {

    // 1. 构建 JSON-RPC 请求
    let request: [String: Any] = [
        "jsonrpc": "2.0",
        "id": id,
        "method": method,
        "params": params
    ]

    // 2. 序列化
    let data = try JSONSerialization.data(
        withJSONObject: request,
        options: []
    )

    // 3. 创建 URLRequest
    var urlRequest = URLRequest(url: rpcURL)
    urlRequest.httpMethod = "POST"
    urlRequest.httpBody = data
    urlRequest.setValue(
        "application/json",
        forHTTPHeaderField: "Content-Type"
    )

    // 4. 发送请求
    let (data, response) = try await URLSession.shared
        .data(for: urlRequest)

    // 5. 解析响应
    guard let json = try JSONSerialization
        .jsonObject(with: data) as? [String: Any] else {
        throw RPCError.invalidResponse
    }

    // 6. 检查错误
    if let error = json["error"] {
        throw RPCError.rpcError(error)
    }

    // 7. 返回结果
    return json["result"]!
}

四、授权请求处理

请求方法：eth_requestAccounts

处理流程：

  1. 钱包收到 eth_requestAccounts 请求
  2. 弹出用户授权弹窗，问用户是否允许 DApp 连接钱包
  3. 用户拒绝 → 返回错误给 DApp
  4. 用户批准 → 返回当前选中账户地址数组给 DApp

Swift 示例：

func handleEthRequestAccounts(id: Int, approved: Bool) {
    guard approved else {
        // 用户拒绝，返回错误
        self.sendErrorResponse(
            id: id,
            message: "User rejected the request"
        )
        return
    }

    // 用户批准，返回地址
    if let address = selectedAccount?.address {
        let result = [formatAddress(address)]
        self.sendSuccessResponse(result: result, id: id)
    } else {
        self.sendSuccessResponse(result: [], id: id)
    }

    // 🔥 重要：账户变化后，需要触发事件通知所有已连接的 DApp
    webView.evaluateJavaScript("""
        if (window.ethereum) {
            window.ethereum.emit('accountsChanged', ['\(formatAddress(address))']);
        }
    """)
}
⚠️ 重要提示：
用户授权连接后，如果切换账户，钱包必须通过 window.ethereum.emit('accountsChanged', [newAddress]) 通知 DApp，否则 DApp 状态会不一致。

五、签名请求处理

签名请求需要用户确认，并使用私钥在原生端完成签名。这是钱包最核心的安全功能。

personal_sign 完整处理流程

1️⃣ 收到请求：参数 [messageHex, address]
↓
2️⃣ 检查地址是否是当前选中账户，不是 → 错误
↓
3️⃣ 将十六进制消息解码为可读字符串（如果是文字）
↓
4️⃣ 弹出签名确认弹窗，给用户看要签名的内容
↓
5️⃣ 用户拒绝 → 返回错误
↓
6️⃣ 用户批准 → 从安全存储取出私钥
↓
7️⃣ 使用 secp256k1 对消息哈希进行签名
↓
8️⃣ 返回 65 字节签名给 DApp（格式 0x...）

Swift 签名示例（使用 TrustWalletCore）

func handlePersonalSign(
    params: Any,
    id: Int,
    selectedAccount: AccountModel,
    approved: Bool
) {
    guard approved else {
        sendErrorResponse(id: id, message: "User rejected signing")
        return
    }

    // 1. 解析参数: personal_sign 参数顺序是 [message, address]
    guard let paramsArray = params as? [Any],
          paramsArray.count >= 2,
          let messageHex = paramsArray[0] as? String,
          let _ = paramsArray[1] as? String else {
        sendErrorResponse(
            id: id,
            message: "Invalid parameters for personal_sign"
        )
        return
    }

    // 2. 将消息从 hex 转为 Data
    let messageData = Data(
        hexString: messageHex.stripHexPrefix()
    )!

    // 3. keccak256 哈希 (Ethereum 签名标准)
    let prefixedMessage = "\x19Ethereum Signed Message:\n"
        + String(messageData.count)
        + String(data: messageData, encoding: .utf8)!

    let prefixedData = prefixedMessage.data(using: .utf8)!
    let hash = Hash.keccak256(data: prefixedData)

    // 4. 获取私钥 (从安全存储)
    // ⚠️ 注意：在真实应用中，私钥应该存在 Keychain，这里简化
    guard let privateKeyData = Data(
        hexString: selectedAccount.privateKey
    ),
          let privateKey = PrivateKey(data: privateKeyData) else {
        sendErrorResponse(id: id, message: "Invalid private key")
        return
    }

    // 5. 签名
    let signature = Secp256k1.sign(
        hash: hash,
        privateKey: privateKey
    )

    // 6. 转为 0x 格式返回
    let signatureHex = "0x" + signature.data.hex

    // 7. 返回给 DApp
    sendSuccessResponse(result: signatureHex, id: id)
}
🔒 安全提醒：
  • 私钥必须存储在安全地方（iOS Keychain），不能存在 UserDefaults 或 plist
  • 签名必须在原生应用内完成，私钥绝对不能传到 JS
  • 签名前必须给用户展示要签名的内容，让用户确认

六、交易处理

eth_sendTransaction 完整流程

1️⃣ DApp 请求：eth_sendTransaction，参数是交易对象
↓
2️⃣ 钱包解码交易：获取 to, value, gasLimit, gasPrice, data
↓
3️⃣ 计算总金额（value + gasLimit × gasPrice），检查余额是否足够
↓
4️⃣ 弹出交易确认弹窗，显示给用户：
  • 发送给谁
  • 多少金额
  • 网络手续费
↓
5️⃣ 用户拒绝 → 返回错误
↓
6️⃣ 用户批准 → 构建 RLP 编码交易
↓
7️⃣ 用私钥对交易进行 ECDSA 签名
↓
8️⃣ 广播签名交易到区块链节点 (eth_sendRawTransaction)
↓
9️⃣ 节点返回交易哈希 → 返回交易哈希给 DApp

广播交易到区块链

签名完成后，需要通过 JSON-RPC eth_sendRawTransaction 广播：

func broadcastSignedTransaction(
    signedTx: Data,
    rpcURL: URL
) async throws -> String {
    let txHex = "0x" + signedTx.hex

    // 使用 eth_sendRawTransaction 广播
    let result = try await forwardToRPC(
        method: "eth_sendRawTransaction",
        params: [txHex],
        id: Int(Date().timeIntervalSince1970),
        rpcURL: rpcURL
    )

    return result as! String
}
方法 区别
eth_sendTransaction 钱包完成签名 并广播，返回 txHash。这是 DApp 最常用的方式。
eth_signTransaction 钱包只签名，返回签名后的交易数据，由 DApp 自己广播。

七、区块链节点服务

钱包需要连接区块链节点才能发送查询和广播交易，常见选项：

服务商 优点 缺点 适合
Infura 稳定，可靠，免费额度够用 中心化服务，需要联网 开源钱包，DApp 浏览器
Alchemy API 丰富，开发者友好，速率限制宽松 中心化服务 生产环境应用
公共节点（例如 BSC 官方节点） 免费，不需要 API Key 限流严格，不稳定 少数特定链
自己运行节点 完全去中心化，不依赖第三方 运行成本高，需要带宽硬盘 高端用户自己托管

多链处理策略：

  • 不同链配置不同的 RPC 端点
  • 根据当前用户选中的账户所在链选择对应的 RPC
  • 主流链建议使用专业节点服务（Infura/Alchemy）保证可用性

八、完整架构总览

DApp 网页 (WKWebView 中)
↓ request
trust-min.js
EIP-1193 Provider 协议转换
↓ window.trustwallet.postMessage
iOS 原生（你的代码）
- 分类请求类型
- 用户弹窗确认
- 私钥签名
↓ 如果只读请求
JSON-RPC 请求 → Infura/Alchemy 节点
↓ 如果签名/交易
原生签名（私钥在 Keychain）
↓ 交易需要广播
广播到节点（eth_sendRawTransaction）
↓ 返回结果
window.ethereum.sendResponse/sendError
↓
trust-min resolve/reject Promise
↓
DApp 得到结果，继续处理
✅ 架构优点总结：
  • ✅ 安全隔离：JS 无法访问私钥，私钥永远在原生
  • ✅ 标准兼容：trust-min 实现标准 EIP-1193，兼容所有 DApp
  • ✅ 职责清晰：trust-min 做协议转换，原生做安全和交互
  • ✅ 易于维护：trust-min 升级不影响原生业务逻辑
